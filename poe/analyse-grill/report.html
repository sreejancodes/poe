# poe: phase orchestrator for Claude Code

A Claude Code plugin with one skill (`poe`) and one subagent (`phase-worker`). It plans a task, splits it into work units sized for about 100k tokens each, and runs each unit in a fresh-context subagent that keeps file-based progress notes.

Requires Claude Code v2.1.296 or later. `analyse` also needs `jupyter` (for `nbconvert`) in the task's environment.

## Installation

This repository is both the plugin and its own marketplace. Add the marketplace, then install the plugin:

```sh
claude plugin marketplace add sreejancodes/poe
claude plugin install poe@poe-tools
```

The same commands work inside a session as `/plugin marketplace add sreejancodes/poe` and `/plugin install poe@poe-tools`. Then run `/reload-plugins` or start a new session.

By default the plugin is installed at **user** scope, so it is available in every project. Add `--scope project` to enable it only for the current repository, recorded in `.claude/settings.json`.

### Update and uninstall

Third-party marketplaces do not update automatically. To get the latest version:

```sh
claude plugin marketplace update poe-tools
claude plugin update poe@poe-tools
```

To remove it:

```sh
claude plugin uninstall poe@poe-tools
claude plugin marketplace remove poe-tools
```

### Offering it to everyone on a project

Commit this to the project's `.claude/settings.json`:

```json
{
  "extraKnownMarketplaces": {
    "poe-tools": { "source": { "source": "github", "repo": "sreejancodes/poe" } }
  },
  "enabledPlugins": { "poe@poe-tools": true }
}
```

Once a collaborator trusts the folder, the marketplace is registered for them. They still need to run `claude plugin install poe@poe-tools --scope project` once.

## Usage

Plugin skills are namespaced, so the command is `/poe:poe`:

```text
/poe:poe plan Build an HPV ORF analysis pipeline with tests and reproducible outputs
/poe:poe grill Build an HPV ORF analysis pipeline with tests and reproducible outputs
/poe:poe grill poe/hpv-orf-analysis/plan.md
/poe:poe split poe/hpv-orf-analysis/plan.md
/poe:poe execute poe/hpv-orf-analysis/plan.md
/poe:poe resume poe/hpv-orf-analysis/plan.md
/poe:poe report poe/hpv-orf-analysis/plan.md
/poe:poe analyse poe/hpv-orf-analysis/plan.md
/poe:poe analyse catch-up
/poe:poe note Plotted ORF lengths per genotype in notebooks/hpv-orf-analysis/orfs.ipynb
```

- **Plan** writes `plan.md` from what you asked for, keeping the approach simple and the code human-readable, then stops. Review the file, edit it or ask for changes, and repeat until you are happy with it. If it finds open decisions that only you can make, it switches to grill instead of guessing.
- **Grill** interviews you before planning. It asks one question at a time in a dialog: pick an option (the recommended one comes first), or type your own answer under Other. Each question shows `Q1 of ~N`, an estimate revised as answers add or remove questions. `grill <task>` starts from scratch and writes `plan.md` once you confirm; `grill <plan-path>` questions an existing plan's assumptions and open points and updates it in place. Decisions are added to `plan.md` under `## Decisions` after every answer; project terms and hard-to-reverse decisions go to the shared `poe/docs/`.
- **Split** takes the reviewed `plan.md` and splits it into phases and work units, each sized for one subagent at roughly 100k tokens. It then stops for approval.
- **Execute** hands each work unit to a fresh `poe:phase-worker` subagent, which writes progress notes as it works. The orchestrator verifies each unit before moving on.
- **Resume** uses the status file and progress notes to continue safely.
- **Report** copies the session's logs and (re)builds `report.html`, a step-by-step view of what the orchestrator and each worker did. Execute and resume also build it automatically at the end, after `summary.md` and the log copy; if the build fails, the reply says so and the task carries on.
- **Analyse** runs data analyses one at a time in a Jupyter notebook; you pick each next one. See [Analysis](#analysis).
- **Analyse catch-up** finds notebook cells poe did not write and logs them, with your confirmation.
- **Note** logs analysis you did yourself, in your own words.

Use `plan` when the task is clear. Use `grill` when you want to be interviewed, or to challenge a draft plan.

Output is deliberately terse: replies point to files instead of repeating them, and plan and split replies end with the next command to paste.

## Analysis

One task can hold both coding and analysis. Use `plan`, `split` and `execute` to build tools and `analyse` to explore data; switch by running the other mode on the same `plan.md`. Phases and analyses share `status.md` and `report.html`.

- **Start**: `/poe:poe analyse <task>`. Without a plan, it writes a short `plan.md` (question, data paths, notebook/output path, environment and how to call `jupyter`) and stops for review. Then run `/poe:poe analyse poe/<task-slug>/plan.md`.
- **Each analysis**: a fresh worker adds cells under a heading `## NN: <question>`, runs the notebook headless (`jupyter nbconvert --to notebook --execute --inplace`), writes a record `poe/<task-slug>/analysis/NN-name.md` and appends an entry to `poe/docs/ANALYSIS_LOG.md`. It proposes 2-3 next analyses; pick one or say done. Done writes `summary.md`, copies logs and builds the report, as execute does. `NN` continues across runs.
- **Notebook rules**: cells poe writes are tagged `poe:<task-slug>/<NN>` in cell metadata. New cells go into the existing notebook; a new notebook is started only when a full re-run takes over ~5 min or the topic changes, and the record says why. Failed attempts are removed from the notebook and described in the record. Notebooks, figures and intermediates live in the project path from `plan.md`, not under `poe/`.
- **Open notebooks**: `--inplace` rewrites the file, so save your edits before an analysis runs. The worker stops with a warning if the notebook was saved by someone else after it read it.
- **Analysis log**: `poe/docs/ANALYSIS_LOG.md` is one chronology for the whole project, across tasks, meant for writing up. Each entry gives the date, question, a one-line result, who did it (poe, user, other agent) and links.
- **Untracked work** (analysis done outside poe, by you or another agent) shows up as untagged code cells. Every `analyse` run starts with a catch-up check (`analyse catch-up` runs it alone): for each group of adjacent untagged cells it drafts a `manual` log entry, asks you to confirm or fix it, appends it and tags the cells `poe:manual` so they are not asked about again. `note <text>` logs such work directly in your words.
- **Well-defined analyses** can also be planned as work units in `split`/`execute`; the worker follows the same notebook rules and writes a record and log entry. Units that write the log run one at a time.
- `report.html` shows analysis records as text; notebooks and figures are not embedded.

Record, log entry and notebook rules in full: [`skills/poe/SKILL.md`](skills/poe/SKILL.md).

## Files

Everything for one task is written under `poe/<task-slug>/` in the directory where Claude Code was started. `poe/` is created if it does not exist. `poe/docs/` is shared across tasks, so `docs` is not used as a task slug.

```
poe/docs/              shared across tasks, written by grill, analyse and note, created when first needed
  GLOSSARY.md          project terms
  adr/NNNN-slug.md     architecture decision records
  ANALYSIS_LOG.md      project-wide analysis log, date order, all tasks
poe/<task-slug>/
  plan.md              what will be built and why
  phases/NN-name.md    one brief per phase, listing its work units
  analysis/NN-name.md  one record per analysis
  status.md            state of every phase and unit
  progress/NN-unit.md  running notes written by each worker
  summary.md           execution summary, written at the end of execute/resume
  report.html          step-by-step report built from the files above and logs/
  logs/<session-id>/   copies of the Claude Code transcripts (.jsonl) of each session, including worker subagents
```

Commit all of `poe/`, including `logs/` and `report.html`. Together with the plan, briefs and progress notes, the transcripts are what make an agentic workflow reproducible: anyone can see what was asked, what each agent did and why. The copied logs contain the full conversation, including file contents and command output, and so does `report.html`. Check them for secrets or data that must not leave the machine before pushing, and add only those paths to `.gitignore` if needed. Do not ignore all of `poe/`, so that `poe/docs/` stays in git.

To build the report by hand, without a Claude Code session (needs Python 3.9 or later, standard library only):

```sh
python3 <plugin>/skills/poe/scripts/poe_report.py poe/<task-slug>
```

`<plugin>` is this repository, or the installed plugin directory. The script writes `poe/<task-slug>/report.html` and prints its path. It is a single HTML file with no external resources, so it opens offline.

Tasks created by older versions in `plans/` can be moved with `mv plans/<slug> poe/<slug>`.

## Thinking text in the report

The report can only show thinking that Claude Code recorded in its transcripts. By default it records none, so each thinking step reads "thinking text not recorded". The overview and each transcript's totals show "thinking recorded: N of M blocks", so you can see whether it was on for a run.

To record it:

- Interactive sessions: set `"showThinkingSummaries": true` in `~/.claude/settings.json` (all projects) or in the project's `.claude/settings.json`. This also shows the summaries in the terminal. Workers are expected to inherit the setting from the session that starts them.
- Headless `claude -p` ignores that setting. Pass the flag instead: `claude -p --thinking-display summarized "..."`.

The recorded text is a summary of the reasoning, not the raw reasoning. Sessions that ran without it cannot be filled in later.

Steps labelled "narration" are short progress updates Claude Code writes alongside thinking; they are shown as they are and not counted as thinking.

## Context settings

The 100k figure is a soft target, not a hard cap. A worker nearing it finishes the step it is in the middle of, updates its progress notes, and returns. The orchestrator then starts a fresh worker from those notes.

`phase-worker` sets `autoCompactWindow: 150000`. This is a backstop above the target, so that automatic compaction does not interrupt a step at exactly 100k. It does not cap cumulative usage. Older Claude Code versions ignore the setting without warning.

The `CLAUDE_CODE_AUTO_COMPACT_WINDOW` environment variable takes precedence over a subagent's `autoCompactWindow`. Setting it to 100000 would make workers compact at 100k regardless, so leave it unset or set it above the target.

## Decision tree

- Task = tree of decisions. A decision depends on others when its options only make sense once they are settled.
- **Frontier** = open decisions whose prerequisites are all settled. Ask one frontier decision at a time; deeper questions wait until their prerequisites are answered.
- `grill <plan-path>`: tree = the plan's assumptions, open points, risky points. Settled `## Decisions` entries are not re-asked.

## Facts vs decisions

- Facts (what the code does, what exists, versions, conventions, test setup): look them up in the code, or with read-only exploration subagents. Never ask the user.
- Decisions (what the user wants, trade-offs only they can weigh): ask.
- Missing detail with an obvious default = not a question. Use the default; note it under Assumptions.

## Questions

- Ask exactly one question per turn: the frontier decision that most other decisions depend on.
- Question counter:
  - Before Q1, estimate N = all open decisions known so far (whole tree, not just frontier), excl. final confirm. `grill <plan-path>` → only the open points being grilled.
  - Prefix every `question`: `Q<k> of ~<N>: `. `~` always shown. `header` unchanged.
  - After each answer, re-estimate N (asked + still open); show the new N on the next question. k +1 per question, never resets within a run; new run after `/clear` restarts at Q1.
  - Final "Matches your understanding?" confirm: no prefix, not counted.
- Ask it with `AskUserQuestion`, one question per call. Never batch questions.
  - `question`: terse, self-contained (the dialog may be all the user sees); include any finding it depends on.
  - `header`: decision label, ≤12 chars.
  - Options: 2–4 concrete, mutually exclusive answers. Recommended first, label ends `(Recommended)`, `description` = short why. Other options' `description` = trade-off.
  - No manual "Other" option (added automatically). `multiSelect` only when answers genuinely combine.
  - `preview` only when comparing concrete artifacts (layouts, snippets).
- Open-ended decision (no sensible option list, e.g. naming a term) → still the dialog: 2 best candidates as options; user types own via "Other".
- Tool unavailable or call rejected → fall back to plain text: one question (same `Q<k> of ~<N>: ` prefix) + `Rec:` line, then stop.
- Pick the next question only after the answer; an answer may add, remove, or change later questions.
- Recommendations follow SKILL.md Plan step 3 "Do not overengineer": simplest option meeting the stated need, repo's existing tools/patterns, no speculative features or config.
- Skip trivia: no question whose answer would not change the plan. A clear task may need one question or none.

## Domain modeling

While grilling, sharpen the language:
- Term used loosely, or two words for one thing → ask which one and what exactly it means.
- Probe a term with a concrete edge-case scenario ("note edited after archiving: still archived?").
- Check terms against existing code names and `poe/docs/GLOSSARY.md`; flag conflicts.

## Writing after every answer

After each answer, before asking the next question:
1. Append the settled decision to `## Decisions` in `poe/<slug>/plan.md` (one bullet: decision + short why).
2. Add or update glossary entries for terms the answer resolved.
3. Write an ADR for any decision that qualifies (below).

Nothing settled lives only in the chat; `/clear` then `grill <plan-path>` must resume without re-asking.

## Glossary

- Path: `poe/docs/GLOSSARY.md`. Create only when the first term is resolved.
- Project-specific terms only. No generic programming words. No implementation detail (file names, classes, schemas).
- Entry format:
  ```
  **Term**: 1–2 sentence definition.
  _Avoid_: synonym, other synonym
  ```
- Keep entries alphabetical; edit an existing entry instead of adding a duplicate.

## ADRs

- Path: `poe/docs/adr/NNNN-slug.md`. Create `adr/` only when the first ADR is written.
- Write one only when all three hold:
  1. Hard to reverse (costly to change later).
  2. Surprising (a future reader would ask "why this way?").
  3. Real trade-off (viable alternatives were rejected).
- Otherwise the decision lives only in `plan.md` `## Decisions`. Zero ADRs is normal.
- Number = highest existing number + 1, 4 digits (`0001` if none). Slug = short kebab-case title.
- Format:
  ```
  # NNNN: <Title>

  <1–3 sentences: context, decision, why.>
  ```
  Add sections (Considered options, Consequences) only when they add real value.

## Finish

- Frontier empty → summarize understanding in ≤5 bullets as plain text, then `AskUserQuestion` "Matches your understanding?": `Yes, write the plan (Recommended)` / `Needs correction`.
- Correction → ask what in plain text; re-ask the affected decisions, one at a time.
- Confirmed → grilling done; continue Grill mode in SKILL.md.

## Context policy: about 100k tokens per agent

- 100k is a **soft target**, not a hard limit. Never claim to know exact token usage unless a tool reports it; otherwise judge by how much has been read and produced.
- Hand over at a natural boundary, not at a number. When a worker nears the target, it finishes the step it is in the middle of (an edit in flight, a test run, a debugging thread that is about to resolve), then brings its progress notes up to date and returns `partial`. Going moderately over the target to finish a coherent step is correct; stopping mid-edit to respect the number is not.
- The orchestrator then starts a **fresh non-fork worker** for the remainder, pointed at the progress notes. Do not keep resuming a bloated agent.

- Avoid unnecessary parallelism, repeated repository scans, duplicate reading, and verbose inter-agent messages.

248	    12	## Decision tree
249	    13	
250	    14	- Task = tree of decisions. A decision depends on others when its options only make sense once they are settled.
251	    15	- **Frontier** = open decisions whose prerequisites are all settled. Ask one frontier decision at a time; deeper questions wait until their prerequisites are answered.
252	    16	- `grill <plan-path>`: tree = the plan's assumptions, open points, risky points. Settled `## Decisions` entries are not re-asked.
253	    17	
254	    18	## Facts vs decisions
255	    19	
256	    20	- Facts (what the code does, what exists, versions, conventions, test setup): look them up in the code, or with read-only exploration subagents. Never ask the user.
257	    21	- Decisions (what the user wants, trade-offs only they can weigh): ask.
258	    22	- Missing detail with an obvious default = not a question. Use the default; note it under Assumptions.
259	    23	
260	    24	## Questions
261	    25	
262	    26	- Ask exactly one question per turn: the frontier decision that most other decisions depend on.
263	    27	- Question counter:
264	    28	  - Before Q1, estimate N = all open decisions known so far (whole tree, not just frontier), excl. final confirm. `grill <plan-path>` → only the open points being grilled.
265	    29	  - Prefix every `question`: `Q<k> of ~<N>: `. `~` always shown. `header` unchanged.
266	    30	  - After each answer, re-estimate N (asked + still open); show the new N on the next question. k +1 per question, never resets within a run; new run after `/clear` restarts at Q1.
267	    31	  - Final "Matches your understanding?" confirm: no prefix, not counted.
268	    32	- Ask it with `AskUserQuestion`, one question per call. Never batch questions.
269	    33	  - `question`: terse, self-contained (the dialog may be all the user sees); include any finding it depends on.
270	    34	  - `header`: decision label, ≤12 chars.
271	    35	  - Options: 2–4 concrete, mutually exclusive answers. Recommended first, label ends `(Recommended)`, `description` = short why. Other options' `description` = trade-off.
272	    36	  - No manual "Other" option (added automatically). `multiSelect` only when answers genuinely combine.
273	    37	  - `preview` only when comparing concrete artifacts (layouts, snippets).
274	    38	- Open-ended decision (no sensible option list, e.g. naming a term) → still the dialog: 2 best candidates as options; user types own via "Other".
275	    39	- Tool unavailable or call rejected → fall back to plain text: one question (same `Q<k> of ~<N>: ` prefix) + `Rec:` line, then stop.
276	    40	- Pick the next question only after the answer; an answer may add, remove, or change later questions.
277	    41	- Recommendations follow SKILL.md Plan step 3 "Do not overengineer": simplest option meeting the stated need, repo's existing tools/patterns, no speculative features or config.
278	    42	- Skip trivia: no question whose answer would not change the plan. A clear task may need one question or none.
279	    43	
280	    44	## Domain modeling
281	    45	
282	    46	While grilling, sharpen the language:
283	    47	- Term used loosely, or two words for one thing → ask which one and what exactly it means.
284	    48	- Probe a term with a concrete edge-case scenario ("note edited after archiving: still archived?").
285	    49	- Check terms against existing code names and `poe/docs/GLOSSARY.md`; flag conflicts.
286	    50	
287	    51	## Writing after every answer
288	    52	
289	    53	After each answer, before asking the next question:
290	    54	1. Append the settled decision to `## Decisions` in `poe/<slug>/plan.md` (one bullet: decision + short why).
291	    55	2. Add or update glossary entries for terms the answer resolved.
292	    56	3. Write an ADR for any decision that qualifies (below).
293	    57	
294	    58	Nothing settled lives only in the chat; `/clear` then `grill <plan-path>` must resume without re-asking.
295	    59	
296	    60	## Glossary
297	    61	
298	    62	- Path: `poe/docs/GLOSSARY.md`. Create only when the first term is resolved.
299	    63	- Project-specific terms only. No generic programming words. No implementation detail (file names, classes, schemas).
300	    64	- Entry format:
301	    65	  ```
302	    66	  **Term**: 1–2 sentence definition.
303	    67	  _Avoid_: synonym, other synonym
304	    68	  ```
305	    69	- Keep entries alphabetical; edit an existing entry instead of adding a duplicate.
306	    70	
307	    71	## ADRs
308	    72	
309	    73	- Path: `poe/docs/adr/NNNN-slug.md`. Create `adr/` only when the first ADR is written.
310	    74	- Write one only when all three hold:
311	    75	  1. Hard to reverse (costly to change later).
312	    76	  2. Surprising (a future reader would ask "why this way?").
313	    77	  3. Real trade-off (viable alternatives were rejected).
314	    78	- Otherwise the decision lives only in `plan.md` `## Decisions`. Zero ADRs is normal.
315	    79	- Number = highest existing number + 1, 4 digits (`0001` if none). Slug = short kebab-case title.
316	    80	- Format:
317	    81	  ```
318	    82	  # NNNN: <Title>
319	    83	
320	    84	  <1–3 sentences: context, decision, why.>
321	    85	  ```
322	    86	  Add sections (Considered options, Consequences) only when they add real value.
323	    87	
324	    88	## Finish
325	    89	
326	    90	- Frontier empty → summarize understanding in ≤5 bullets as plain text, then `AskUserQuestion` "Matches your understanding?": `Yes, write the plan (Recommended)` / `Needs correction`.
327	    91	- Correction → ask what in plain text; re-ask the affected decisions, one at a time.
328	    92	- Confirmed → grilling done; continue Grill mode in SKILL.md.

382	    53	Plugin skills are namespaced, so the command is `/poe:poe`:

397	    68	- **Plan** writes `plan.md` from what you asked for, keeping the approach simple and the code human-readable, then stops. 412	    83	
413	    84	One task can hold both coding and analysis. Use `plan`, `split` and `execute` to build tools and `analyse` to explore data; switch by running the other mode on the same `plan.md`. Phases and analyses share `status.md` and `report.html`.
414	    85	
415	    86	- **Start**: `/poe:poe analyse <task>`. Without a plan, it writes a short `plan.md` (question, data paths, notebook/output path, environment and how to call `jupyter`) and stops for review. Then run `/poe:poe analyse poe/<task-slug>/plan.md`.
416	    87	- **Each analysis**: a fresh worker adds cells under a heading `## NN: <question>`, runs the notebook headless (`jupyter nbconvert --to notebook --execute --inplace`), writes a record `poe/<task-slug>/analysis/NN-name.md` and appends an entry to `poe/docs/ANALYSIS_LOG.md`.
