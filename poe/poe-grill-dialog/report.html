## Assumptions

- `AskUserQuestion` limits: 1–4 questions/call, 2–4 options/question, header ≤12 chars, "Other" free-text added automatically.
- Skill frontmatter has no `allowed-tools` restriction → tool callable from the skill.
- One-question-per-turn was a deliberate choice (answers reshape later questions) → kept.

## Approach

Replace GRILLING.md `## Questions` rules:

- Remove `Plain text only. No AskUserQuestion.` and the `Q<n>. / Rec:` format block and the `"yes" = accept the rec` reply rule.
- Ask every decision with `AskUserQuestion`, one question per call:
  - `question`: terse, self-contained (dialog may be all the user sees) — include any finding it depends on.
  - `header`: ≤12-char decision label.
  - Options: 2–4 concrete, mutually exclusive answers. Recommended first, label ends `(Recommended)`; its `description` = short why. Other descriptions = trade-off.
  - No "Other" option (automatic). `multiSelect` only when answers genuinely combine.
  - `preview` only when comparing concrete artifacts (layouts, snippets).
- Open-ended decision (no sensible option list, e.g. naming a term) → still the dialog: 2 best candidate answers as options; user uses "Other" for own.
- Tool unavailable or call rejected (non-interactive session) → fall back to plain text: one question + `Rec:` line, then stop.
- Unchanged: one frontier decision per turn; next question picked only after the answer; write decisions/glossary/ADRs after every answer, before the next dialog; skip trivia; recs follow "Do not overengineer".

`## Finish`:
- Summary (≤5 bullets) as plain text, then `AskUserQuestion`: "Matches your understanding?" → `Yes, write the plan (Recommended)` / `Needs correction`. Correction → ask what via follow-up text, re-ask affected decisions.

- 4-option cap forces lossy option lists. Mitigation: "Other" always available; options = best candidates only.

## Decision tree

- Task = tree of decisions. A decision depends on others when its options only make sense once they are settled.
- **Frontier** = open decisions whose prerequisites are all settled. Ask one frontier decision at a time; deeper questions wait until their prerequisites are answered.
- `grill <plan-path>`: tree = the plan's assumptions, open points, risky points. Settled `## Decisions` entries are not re-asked.

## Facts vs decisions

- Facts (what the code does, what exists, versions, conventions, test setup): look them up in the code, or with read-only exploration subagents. Never ask the user.
- Decisions (what the user wants, trade-offs only they can weigh): ask.
- Missing detail with an obvious default = not a question. Use the default; note it under Assumptions.

## Questions

- Plain text only. No AskUserQuestion.
- Ask exactly one question per turn: the frontier decision that most other decisions depend on.
- Format: one terse question + `Rec:` recommended answer (+ short why when not obvious).
- Then stop and wait. Never ask a second question in the same turn.
- Reply rules, stated once with the first question: "yes" = accept the rec; anything else = the answer.
- Pick the next question only after the answer; an answer may add, remove, or change later questions.
- Recommendations follow SKILL.md Plan step 3 "Do not overengineer": simplest option meeting the stated need, repo's existing tools/patterns, no speculative features or config.
- Skip trivia: no question whose answer would not change the plan. A clear task may need one question or none.

Format:
```
Q<n>. <question>
    Rec: <answer>
```

## Domain modeling

While grilling, sharpen the language:
- Term used loosely, or two words for one thing → ask which one and what exactly it means.
- Probe a term with a concrete edge-case scenario ("note edited after archiving: still archived?").
- Check terms against existing code names and `poe/docs/GLOSSARY.md`; flag conflicts.

## Writing after every answer

After each answer, before asking the next question:
1. Append the settled decision to `## Decisions` in `poe/<slug>/plan.md` (one bullet: decision + short why).
2. Add or update glossary entries for terms the answer resolved.
3. Write an ADR for any decision that qualifies (below).

Nothing settled lives only in the chat; `/clear` then `grill <plan-path>` must resume without re-asking.

## Glossary

- Path: `poe/docs/GLOSSARY.md`. Create only when the first term is resolved.
- Project-specific terms only. No generic programming words. No implementation detail (file names, classes, schemas).
- Entry format:
  ```
  **Term**: 1–2 sentence definition.
  _Avoid_: synonym, other synonym
  ```
- Keep entries alphabetical; edit an existing entry instead of adding a duplicate.

## ADRs

- Path: `poe/docs/adr/NNNN-slug.md`. Create `adr/` only when the first ADR is written.
- Write one only when all three hold:
  1. Hard to reverse (costly to change later).
  2. Surprising (a future reader would ask "why this way?").
  3. Real trade-off (viable alternatives were rejected).
- Otherwise the decision lives only in `plan.md` `## Decisions`. Zero ADRs is normal.
- Number = highest existing number + 1, 4 digits (`0001` if none). Slug = short kebab-case title.
- Format:
  ```
  # NNNN: <Title>

12	## Decision tree
13	
14	- Task = tree of decisions. A decision depends on others when its options only make sense once they are settled.
15	- **Frontier** = open decisions whose prerequisites are all settled. Ask one frontier decision at a time; deeper questions wait until their prerequisites are answered.
16	- `grill <plan-path>`: tree = the plan's assumptions, open points, risky points. Settled `## Decisions` entries are not re-asked.
17	
18	## Facts vs decisions
19	
20	- Facts (what the code does, what exists, versions, conventions, test setup): look them up in the code, or with read-only exploration subagents. Never ask the user.
21	- Decisions (what the user wants, trade-offs only they can weigh): ask.
22	- Missing detail with an obvious default = not a question. Use the default; note it under Assumptions.
23	
24	## Questions
25	
26	- Plain text only. No AskUserQuestion.
27	- Ask exactly one question per turn: the frontier decision that most other decisions depend on.
28	- Format: one terse question + `Rec:` recommended answer (+ short why when not obvious).
29	- Then stop and wait. Never ask a second question in the same turn.
30	- Reply rules, stated once with the first question: "yes" = accept the rec; anything else = the answer.
31	- Pick the next question only after the answer; an answer may add, remove, or change later questions.
32	- Recommendations follow SKILL.md Plan step 3 "Do not overengineer": simplest option meeting the stated need, repo's existing tools/patterns, no speculative features or config.
33	- Skip trivia: no question whose answer would not change the plan. A clear task may need one question or none.
34	
35	Format:
36	```
37	Q<n>. <question>
38	    Rec: <answer>
39	```
40	
41	## Domain modeling
42	
43	While grilling, sharpen the language:
44	- Term used loosely, or two words for one thing → ask which one and what exactly it means.
45	- Probe a term with a concrete edge-case scenario ("note edited after archiving: still archived?").
46	- Check terms against existing code names and `poe/docs/GLOSSARY.md`; flag conflicts.
47	
48	## Writing after every answer
49	
50	After each answer, before asking the next question:
51	1. Append the settled decision to `## Decisions` in `poe/<slug>/plan.md` (one bullet: decision + short why).
52	2. Add or update glossary entries for terms the answer resolved.
53	3. Write an ADR for any decision that qualifies (below).
54	
55	Nothing settled lives only in the chat; `/clear` then `grill <plan-path>` must resume without re-asking.
56	
57	## Glossary
58	
59	- Path: `poe/docs/GLOSSARY.md`. Create only when the first term is resolved.
60	- Project-specific terms only. No generic programming words. No implementation detail (file names, classes, schemas).
61	- Entry format:
62	  ```
63	  **Term**: 1–2 sentence definition.
64	  _Avoid_: synonym, other synonym
65	  ```
66	- Keep entries alphabetical; edit an existing entry instead of adding a duplicate.
67	
68	## ADRs
69	
70	- Path: `poe/docs/adr/NNNN-slug.md`. Create `adr/` only when the first ADR is written.
71	- Write one only when all three hold:
72	  1. Hard to reverse (costly to change later).
73	  2. Surprising (a future reader would ask "why this way?").
74	  3. Real trade-off (viable alternatives were rejected).
75	- Otherwise the decision lives only in `plan.md` `## Decisions`. Zero ADRs is normal.
76	- Number = highest existing number + 1, 4 digits (`0001` if none). Slug = short kebab-case title.
77	- Format:
78	  ```
79	  # NNNN: <Title>
80	
81	  <1–3 sentences: context, decision, why.>
82	  ```
83	  Add sections (Considered options, Consequences) only when they add real value.
84	
85	## Finish
86	
87	- Frontier empty → summarize understanding in ≤5 bullets; ask the user to confirm it matches theirs.
88	- Correction → re-ask the affected decisions, one at a time.
89	- Confirmed → grilling done; continue Grill mode in SKILL.md.
